- **THE ROOT CAUSE, finally understood:** VLC's contrib Qt is built as **static libraries** — the official `libqt_plugin.dll` has all of Qt *baked in*, zero Qt DLL dependencies. **MSYS2's Qt is shared** (`Qt6Core.dll` + friends), so our `libqt_plugin.dll` has ~33 external DLL deps. VLC 4.0's loader (`src/win32/plugin.c`) loads every plugin with `LoadLibraryExW(path, NULL, LOAD_LIBRARY_SEARCH_SYSTEM32)` — System32 only, no app dir, no plugin dir, and (without `LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`) not even the plugin's own directory for its dependencies. So a shared-Qt plugin **cannot** resolve its Qt DLLs no matter where we put them (short of System32). This is why the MSYS2-Qt path was always going to end here.
- **The fix (proposed to Nathan, awaiting his OK):** patch `src/win32/plugin.c` `vlc_dlopen()` to `AddDllDirectory()` the plugin's own folder and load with `LOAD_LIBRARY_SEARCH_SYSTEM32 | LOAD_LIBRARY_SEARCH_USER_DIRS | LOAD_LIBRARY_SEARCH_DLL_LOAD_DIR`, so a plugin can resolve its dependency DLLs from beside itself; then put the 33 Qt DLLs next to `libqt_plugin.dll`. Rebuilds only `libvlccore` (~2 min). Mildly relaxes VLC's plugin-load hardening. Alternative is still building contrib Qt static (1–2 h).
