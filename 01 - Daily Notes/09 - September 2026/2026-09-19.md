## Session 1: the camera wall

### What Got Done

- **Built [[camera-wall]]**, a local web app that shows every IP camera on one page. It lives in
  `04 - Resources/camera-wall/`. Node 22, zero npm dependencies (including a hand-written
  WebSocket server and MP4 fragment splitter), with `ffmpeg` as the only prerequisite.
- **The video path:** camera → ffmpeg → fragmented MP4 over a WebSocket → Media Source Extensions
  in the browser. H.264 is repackaged rather than re-encoded, so the CPU cost is near zero. H.265
  cameras are detected on connect and re-encoded, because browsers will not play H.265 reliably.
  Streams only run while someone is watching and stop about 20 seconds after the last viewer.
- **Two fallbacks under that:** server-side JPEG over `multipart/x-mixed-replace` (iPhone Safari
  has no Media Source Extensions, and it also catches any browser that refuses the codec), and a
  stills-only mode that polls one JPEG every few seconds for a laptop on battery.
- **Brand support for the "app camera" brands:** Tapo, Kasa, Reolink, Hikvision, Annke, Lorex,
  Dahua, Amcrest, Imou, EZVIZ, Foscam, Swann, Axis, Vivotek, UniFi, Wyze, Eufy and generic ONVIF
  (Yi, Tuya and VicoHome were added in session 2),
  each with its RTSP URL shape and the quirk that catches people out (Tapo needs a separate camera
  account, EZVIZ wants the code printed on the body, and so on).
- **A discovery command** (`npm run discover`): ONVIF multicast probe plus a port sweep of the
  local /24, brands guessed from MAC prefixes, writes a starter config. And `npm run check`, which
  tests every camera and says in plain words what is wrong with the ones that fail.
- **Tested it properly** against fake cameras built out of ffmpeg (H.264 and H.265 over HTTP).
  The stream captured over the WebSocket came back a valid MP4 — 278 frames, 18.5 seconds,
  640x360 H.264, decodes frame-perfect. H.265 auto-re-encodes. Snapshots, the JPEG fallback,
  stills mode, the focus view and the camera picker all render in a real browser. Unplugging a
  camera mid-stream shows it unreachable and it recovers by itself when plugged back in.
- **Four real bugs found by testing rather than reading:** a wrong RFC 6455 GUID (the WebSocket
  handshake was rejected by every browser), an unhandled socket error that took the whole server
  down when a viewer disconnected, a `hidden` focus panel that still swallowed every click, and a
  camera with an explicit URL silently getting a brand template built from an empty host.

### What's Still In Progress

- Nothing here has met a real camera yet. Three steps, all on the camera side, are in
  [[Active Priorities]]: install ffmpeg, switch RTSP on in each camera's app, then `discover` and
  `check` to fill in `cameras.json`.
- Live H.264 playback in a browser is the one thing not verified, because the headless Chromium in
  the build environment has no H.264 decoder. Everything up to the decoder was verified, and
  Chrome and Edge on Windows both decode H.264.

### Decisions Made

- **Local RTSP, not vendor APIs.** Every brand's cloud API needs an account, breaks on their
  schedule, and sends the video on a round trip to a data centre. Reading the cameras' own streams
  on the LAN is faster, private, and does not rot.
- **Cloud-only cameras get an honest tile, not a fake one.** Ring, Blink, Nest and Arlo have no
  local stream at all. Rather than pretend, those tiles say so and link to the vendor app, with
  the bridge that could pull them in named in the docs.
- **No npm dependencies.** This has to still run in two years on a freshly wiped Windows box, and
  `npm install` is the part that rots.
- **Password on by default, bound to localhost.** The page can see every camera in the house.
  Given [[Security incident 2026-09-12]], credentials can also live in environment variables
  rather than in the config file, and never reach the browser.
- **No recording or motion detection.** It is a wall of live pictures. Frigate and Blue Iris
  already do events well, and half-doing that here would be worse than not doing it.

  prints every path that answers with codec and resolution, and ends with a config entry ready to
  paste (credentials masked). Tested against a stubbed camera — it found main and sub and picked
  them apart by resolution — and against a dead host for the nothing-found path.

### Decisions Made

- **No ONVIF `GetStreamUri`.** It would ask an ONVIF camera for its URL directly, but the
  WS-Security auth cannot be verified here without a camera on the network, and a wrong
  implementation reports false negatives that look like "your camera has no stream". The path
  probe measures the same thing empirically. Revisit once there is hardware to test against.

## Session 3: Tuya confirmed, and what that changed

### What Got Done

- **Nathan confirmed "Smart home" is Tuya Smart Life**, so I checked the current facts rather than
  trusting what I had written from memory — and three of them were wrong or missing.
- **Tuya uses port 6554**, not 554, on most models (some use 8554), and the paths are `/stream0`
  or `/stream_0` rather than the Tapo-style `/stream1`. The prober was checking neither. It now
  checks 554, 6554 and 8554, and 35 paths, and it knocks on each port first so a closed one costs
  a second instead of 35 timeouts.
- **The app-side steps are specific:** camera Settings > ONVIF ("Onvif Switch") > on, then Reset
  Password with a capital letter in it. The username is then always `admin`, never the Smart Life
  login. That is in the brand note, the README and [[Active Priorities]].
- **Built `"url": "auto"`.** Some Tuya firmwares change their RTSP path after a reboot, so a
  written-down URL is not enough. An `auto` camera gets probed on first use, the port and path are
  remembered in `.camera-wall-urls.json` beside the config, and after two failures in a row it
  goes looking again. The cache holds only the port and path — credentials stay in `cameras.json`
  and are pasted back on at use time.
- **Found the right bridge for the cloud-only models:** go2rtc has a native `tuya://` source that
  signs in with the Smart Life account and re-serves the camera as plain RTSP. It is a single .exe
  on Windows, which suits this machine. Verified the source exists and the URL syntax
  (`tuya://<region-host>?device_id=&email=&password=`) by reading go2rtc's own code, not from
  memory. This replaces the tuya-ipc-terminal suggestion from session 2.

### Decisions Made

- **Check the facts before writing the guide.** Session 2's Tuya advice was written from memory
  and had the wrong port, the wrong paths and a worse bridge. Anything a future session will act
  on gets verified against a source first.
